# Доменная документация

Как инженерные скиллы должны потреблять доменную документацию репозитория при исследовании кодовой базы.

## Перед исследованием прочитайте

- **`GLOSSARY.md`** в корне репозитория, или
- **`GLOSSARY-MAP.md`** в корне, если он существует: указывает на один `GLOSSARY.md` на контекст. Прочитайте каждый, относящийся к теме.
- **`docs/adr/`**: прочитайте ADR, затрагивающие область, в которой предстоит работать. В multi-context репозиториях проверяйте также `src/<context>/docs/adr/` на решения в рамках контекста.

Если каких-то из этих файлов нет — **продолжайте молча**. Не отмечайте их отсутствие и не предлагайте создавать их заранее. Скилл `/domain-modeling` (достижим через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения реально разрешаются.

## Структура файлов

Single-context репозиторий (большинство репозиториев):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Multi-context репозиторий (наличие `GLOSSARY-MAP.md` в корне):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← общесистемные решения
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← решения конкретного контекста
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Используйте словарь глоссария

Когда ваш вывод называет доменное понятие (в заголовке issue, предложении рефакторинга, гипотезе, имени теста), используйте термин так, как он определён в `GLOSSARY.md`. Не дрейфуйте к синонимам, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо вы изобретаете язык, которым проект не пользуется (пересмотрите), либо есть реальный пробел (отметьте для `/domain-modeling`).

## Отмечайте конфликты с ADR

Если ваш вывод противоречит существующему ADR, укажите это явно, а не переопределяйте молча:

> _Противоречит ADR-0007 (event-sourced orders), но стоит пересмотреть, потому что…_
